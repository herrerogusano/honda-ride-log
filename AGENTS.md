# Agent guide

Static web (Vite + TypeScript, no framework) that shows a rider their own
route statistics. It is a browser client of a separate invitation-only
service; it has no backend. **Read `docs/PLAN.md` first**: it holds the
decisions, the privacy rules, the design and the checked and unchecked
technical facts.

## Hard rules

- This repository is public. Never commit personal data, real
  identifiers (route ids, plates, VINs, emails, coordinates of real rides),
  tokens or anything copied from a real account. Fixtures are synthetic and
  generated by `src/demo/`. One exception, by the owner's decision: the
  `production` entry of `environments.config.json` holds the three public
  values of the production service (address, login domain, web client id),
  and the `cloudflare` entry those of the open service's production
  deployment plus its public Turnstile site key. Values of any other
  deployment stay out of the repository.
- Privacy rules in `docs/PLAN.md` are requirements, not suggestions. Data
  from the service goes through `src/domain/sanitize.ts` before anything else
  touches it.
- No third-party requests except OpenStreetMap tiles and exactly two visit
  counters (`docs/PLAN.md`, section 17): Cloudflare Web Analytics, and
  Google Analytics 4 only after the visitor accepts in the cookie notice (if
  not, its script is never requested). Both are off while
  `analytics.config.json` is empty. They get the visit and the closed list
  of events in `src/analytics/`, never a route, a figure, an identifier,
  anything of the sign-in or the full address, and they start only after
  the page has dealt with the return from the login. They never share a
  page load with the open service's screen before the login, where the
  email is typed (`seal()`, `docs/PLAN.md` section 18). They are started from
  `src/main.ts` only. One more, only in a build for the open service
  (`access: "public"` in `environments.config.json`, `docs/PLAN.md`
  section 18): Cloudflare Turnstile (`challenges.cloudflare.com`, script
  and frame), loaded only on the screen before the login and given nothing
  but its own check; the email goes only to the service's `/pase` and as
  the login hint. An invitation build does not even allow its origin.
  Any other third party (another analytics or tag
  service, fonts, a CDN, embeds) stays banned: `tests/csp.test.ts` pins the
  full list of foreign origins. The Content Security Policy lives in
  `csp.config.json`; changing it needs a written reason in `docs/PLAN.md`
  and a matching change in `tests/csp.test.ts`.
- No `innerHTML` or other HTML-string sinks, no inline scripts, styles or
  handlers. No browser storage and no cookies, with four one-file
  exceptions recorded in `docs/PLAN.md`: `src/storage/maintenance.ts` may
  use `localStorage` (and only `localStorage`) for the two service-interval
  numbers the user types; `src/auth/pendingLogin.ts` may use
  `sessionStorage` (and only `sessionStorage`) for the PKCE verifier and the
  `state` while the browser goes to the login page and back (and, in the
  open service only, the fixed word `delete_unconfirmed` across the trip
  to its sign-out page), imported only by `src/auth/login.ts`; and `src/storage/consent.ts` may use
  `localStorage` for the answer to the cookie notice and `document.cookie`
  only to delete Google Analytics' cookies, imported only by
  `src/analytics/tracker.ts`; and `src/auth/savedSession.ts` may use
  `sessionStorage` (and only `sessionStorage`) for the access token and its
  expiry, so a reload keeps the session, imported only by
  `src/auth/login.ts` and removed when the session ends; in a second entry,
  bound to that token and removed with it, the same file keeps the
  account data as `src/domain/sanitize.ts` makes it (`accountSnapshot`:
  route dates, km, durations, speeds and inferred flag, and the vehicle's
  battery, odometer, last use, model and mileage), so a reload paints
  without asking the service. Never a trace, a start or end place, a route
  id (`RouteRef` stays sealed: the loader finds a kept route again in the
  light list), an email or the token in that entry. No visit counter
  loads in a page load that holds that token (`src/boot.ts` seals them).
  The token goes nowhere else (not `localStorage`, the address, the title,
  the console, the counters or an error). A change that needs another exception opens it for a single
  file, records it there and in `tests/lint-storage.test.ts`.
  (ESLint and `scripts/check-dist.mjs` catch the common forms; they are a
  net, not a proof).
- Route ids and untrimmed traces are sealed handles. Do not widen the
  ESLint import rules that guard `serviceRouteId`, `untrimmedLines` and
  `sensitivePlaces`. The whole trace is drawn on the signed-in rider's
  screen only (owner's decision, `docs/PLAN.md` section 4): it leaves
  `src/domain/trim.ts` through `screenTrace`, which only
  `src/ui/traceStore.ts` may import; that store is sealed too (only
  `src/ui/app.ts`, `src/ui/mapView.ts` and `src/ui/atlas/atlasView.ts`). Anything that
  can leave the screen (share card, downloads, images, analytics) carries
  no trace, or `trimTrace` if it ever must; never `screenTrace`.
- Runtime dependencies: Leaflet only. Charts are hand-written SVG.
- User-facing text is Spanish. Code, comments and commit messages are English.

## Trying the open service locally

Put the values of a public deployment in the `development` entry of
`environments.config.json` as an uncommitted change (`access: "public"`,
`turnstileSiteKey`, the service values and `http://localhost:5173/` as
return and sign-out address), then `npm run dev`. To see the security
policy at work, `npx vite build --mode development` and
`npx vite preview --mode development --port 5173 --strictPort` (open
`http://localhost:5173/honda-ride-log/`): the service only answers CORS
from `http://localhost:5173`. Put the entry back before committing; the
tests expect it empty.

## Commands

```sh
npm ci
npm run lint
npm run typecheck
npm test
npm run build   # typecheck + vite build + publication checks on dist/
```

On Windows, stop any running `npm run dev` or `vite preview` before
`npm ci`: they hold files in `node_modules` and the install fails. The
preview server uses port 4173; if another process holds it, Vite picks the
next free port, so read the address it prints instead of assuming 4173.

## Process

- Small pull requests against `main`; CI (lint, tests, build) must be green
  and an independent reviewer must have looked at the change before a
  merge: PullBeacon (comment `@pullbeacon review` on the PR; review only,
  `.pullbeacon.yml`) reads the diff, and a browser check at phone and desktop
  widths covers what it cannot see. Changes to privacy, data or sign-in code
  also get a reviewer agent that runs the tests and breaks the code on
  purpose. No direct pushes to `main`.
- If CI does not start on a pull request, close and reopen it to trigger
  the run again. Wait for CI as its own step and read the result before
  merging; never chain a watch command with the merge.
- Fixes made after a review are listed in the pull request (a comment or the
  description), so the reviewer can see what changed since their read; a
  fix to privacy, data or sign-in code gets another review.
- Pull request titles and descriptions, commit messages and PR comments are
  public: say what changes and how it was checked. No costs, billing,
  credits or account details, no owner's reasons or quotes, no local paths,
  no names of agent threads or roles. That context belongs in the owner's
  private notes, not here.
- Every new test must be seen failing once with broken data before it counts.
- A green test against a fake proves the contract as we read it, not that
  the real service behaves that way. Say which one you ran.
